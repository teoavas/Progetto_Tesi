Il sistema è sviluppato come un'unica catena a colpo singolo, l'esito dell'esecuzione non viene restituito al modello per una nuova generazione: si vuole misurare cosa produce il modello senza correzioni successive. La funzione del dataset entra due volte nel processo: per poter generare il prompt da fornire al modello e in fase di esecuzione dove viene scritta accanto ai test perché possano importarla (è su di essa che si misura la copertura).
La biforcazione finale separa la parte statica (ciò che si stabilisce senza eseguire i test) dalla parte dinamica. La normalizzazione come mostrato in figura rimuove la presenza di markdown nei test generati: un blocco di codice in stile markdown in cima al file in cima rende il file sintatticamente non valido, e il campione finirebbe fra i non eseguibili per un motivo di formattazione anziché di contenuto. Togliendolo prima di salvare, il dato sparisce, e il rispetto di quel vincolo non è più verificabile a posteriori.


\section{Formalizzazione}
\label{sec:formalizzazione}

La formalizzazione che segue serve a rendere il resto del capitolo più leggibile e a fissare i simboli usati nel Capitolo~\ref{ch:risultati}

Sia $\mathcal{F}$ l'insieme delle funzioni sotto test e $\mathcal{M}$ l'insieme
dei modelli considerati, con $|\mathcal{F}| = 100$ e $|\mathcal{M}| = 3$. Per
ogni coppia $(m, f)$ con $m \in \mathcal{M}$ e $f \in \mathcal{F}$ il sistema
produce un file di test, secondo la catena

\begin{equation}
T(m, f) = N\bigl(m(P(f))\bigr),
\label{eq:catena}
\end{equation}

dove:

\begin{itemize}
  \item $P(f)$ è il prompt costruito a partire dalla funzione $f$ tramite il
        template fisso descritto nella Sezione~\ref{sec:prompt};
  \item $m(\cdot)$ indica l'invocazione del modello a parametri costanti;
  \item $N(\cdot)$ è la normalizzazione della risposta;
  \item $T(m, f)$ è il file di test risultante.
\end{itemize}

Si indica inoltre con $t \in T(m, f)$ la singola funzione di test contenuta nel
file. La distinzione fra $T(m,f)$ e $t$ è sostanziale: le metriche di esito, che
classificano come si è conclusa l'esecuzione dell'intero file, sono definite su
$T(m,f)$; quelle di correttezza, che contano quanti test risultano giusti, sono
definite sul singolo $t$.

\section{Dataset e selezione dei campioni}
Le funzioni Python sfruttate per lo sviluppo del lavoro sono state prese dal dataset pubblico ULT\_Lite \cite{huang2025ult}, in tutto 200 campioni in formato JSON Lines. Del totale, sono stati usati i primi 100 campioni per ordine di apparizione nel file (criterio deterministico e riproducibile).

Ogni campione contiene il nome della funzione, il codice sorgente, la descrizione in linguaggio naturale, un identificativo e una lista di assert. Le funzioni hanno una lunghezza mediana di 34 righe, con un minimo di 8 e un massimo di 171.

Tutte le funzioni del benchmark hanno complessità ciclomatica non inferiore a
dieci~\cite{mccabe1976complexity}: come riportato nella Sezione~\ref{sec:bench},
è il criterio con cui gli autori gli autori escludono il codice banale e spiega perché gli esempi che seguono contengono molte diramazioni in poche righe.

Un esempio della difficoltà posta dal benchmark è riportato nel
Listato~\ref{lst:checkformulas}. I parametri si chiamano \texttt{arguments}, \texttt{formulaTuple} e \texttt{state}, e non ci sono annotazioni di tipo né documentazione. Dalla sola firma non si può dedurre che \texttt{formulaTuple} contenga tuple di lunghezza uno, due o tre. È quindi il modello a dover ricavare la struttura attesa degli argomenti dal corpo della funzione. è il caso concreto
dei formati di input impliciti descritti nella Sezione~\ref{sec:testing}.

\begin{lstlisting}[float=htbp,
                   caption={Il campione 84 del dataset, \texttt{checkFormulas}.},
                   label={lst:checkformulas}]
def checkFormulas(arguments, formulaTuple, state):
    for formula in formulaTuple:
        if len(formula) == 1 and formula[0] not in state:
            return False
        if len(formula) == 2 \
            and (formula[0] not in state or arguments[formula[1]] not in state[formula[0]]):
            return False
        if len(formula) == 3 \
            and (formula[0] not in state or (arguments[formula[1]], arguments[formula[2]]) not in state[formula[0]]):
            return False
    return True
\end{lstlisting}

La descrizione in linguaggio naturale non viene passata al modello: in questo modo quest'ultimo deve essere in grado di ricavare da solo il comportamento atteso della funzione. La lista di assert non è utilizzabile come riferimento: gli autori del benchmark dichiarano di non rilasciare i test corretti di riferimento  (\emph{ground truth}) per non contaminare i futuri addestramenti.
Il Listato~\ref{lst:degree} ne è un esempio: fra le asserzioni fornite per quella funzione compare \texttt{is\_degree\_in\_degree\_range(30, 150, 100) == True},
mentre il codice del dataset restituisce \texttt{False}.

\begin{lstlisting}[float=htbp,
                   caption={Il campione 0 del dataset, \texttt{is\_degree\_in\_degree\_range}.},
                   label={lst:degree}]
def is_degree_in_degree_range(degree_a, degree_b, degree_c):
    degrees_omni = [degree_a, degree_b, degree_c]
    for x in range(len(degrees_omni)):
        if degrees_omni[x] > 180 or degrees_omni[x] <= -180:
            degrees_omni[x] = -180 * (((degrees_omni[x] // 180) % 2) \
                * degrees_omni[x]/abs(degrees_omni[x])) + (degrees_omni[x] % 180)
    degree_a = degrees_omni[0]
    degree_b = degrees_omni[1]
    degree_c = degrees_omni[2]
    clockwise = degree_a
    counterclock = degree_b
    if clockwise > counterclock:
        if degree_c <= clockwise and degree_c >= counterclock:
            return True
    elif clockwise < counterclock and clockwise <= 0 and counterclock > 0:
        if degree_c >= counterclock or degree_c <= clockwise:
            return True
    return False
\end{lstlisting}


\section{Costruzione del prompt}
A ciascuno dei modelli usati è stato fornito il medesimo prompt $P(f)$ riportato nel Listato~\ref{lst:prompt}: in questo modo le differenze osservate sono attribuibili al modello e non alla formulazione. Ognuno dei vincoli riportati nella parte \texttt{[instruction]} ha una ragione operativa di primaria importanza. Chiedere di scrivere i file in stile pytest senza classi e con import esplicito consente l'eseguibilità del file in isolamento accanto alla sua funzione $f$ di riferimento. Il fatto di scrivere da 3 a 8 funzioni pone un vincolo sull'output in modo tale che il numero di token sia sufficiente a contenerlo e allo stesso tempo rende i file meglio confrontabili tra modelli. I nomi numerati permettono di individuare il singolo test: è la base per la metrica Pass@1. Il fatto di avere almeno un assert dà la sicurezza che ogni test abbia dietro un oracolo e non si limiti a chiamare la funzione. Il divieto di sovrascrizione della funzione vincola il modello ad attenersi alla funzione $f$ del dataset, in caso contrario le metriche sulla copertura non avrebbero alcun significato perché verrebbero valutate sulla copia.
L'assenza di spiegazioni e markdown rende l'output $T(m,f)$ un file Python direttamente eseguibile.

Infine, la descrizione di come il modello $m$ dovrebbe portare a termine il compito viene riportata nella parte di \texttt{[format]}: per i modelli più piccoli vale la pena mostrare quella che dovrebbe essere la forma attesa rispetto ad una spiegazione in linguaggio naturale.

\begin{lstlisting}[language=,
                   caption={Il template del prompt, identico per tutti i modelli
                            e tutti i campioni. I segnaposto \texttt{func\_name}
                            e \texttt{code} vengono sostituiti con il nome e il
                            codice della funzione sotto test.},

[instruction]
Write unit tests in Python for the function given below.

[data]
{code}

\section{Modelli e parametri}

I tre modelli linguistici utilizzati in questo lavoro fanno parte della famiglia Llama~\cite{llama3herd} e sono di dimensione crescente, rispettivamente da uno, tre e otto miliardi di parametri, corrispondenti all'identificativo \texttt{llama3.2:1b}, \texttt{llama3.2:3b} e \texttt{llama3.1:8b}. I primi due sono Llama 3.2 mentre il terzo fa parte di Llama 3.1: è stato necessario passare alla versione 3.1 in quanto 1b e 3b sono gli unici modelli esclusivamente testuali della versione 3.2.
Questi modelli sono stati valutati a parità di prompt e parametri: la temperatura è stata fissata a 0. Questo significa, dalla definizione di temperatura, che il modello sceglie sempre il token più probabile. In questo modo la generazione diventa deterministica e si è scelto quindi di svolgere una singola esecuzione per ogni campione.
Il limite dei token è stato posto pari a 1024 per l'output. Rispettare il vincolo sul numero di test non garantisce però di rientrare nel limite di token: alcuni file contengono correttamente 3, 5, 6, 7 funzioni di test ma sono comunque troncati perché i singoli test scritti potrebbero essere verbosi a tal punto da far esaurire il budget.

L'esecuzione è stata fatta in locale tramite Ollama \cite{ollama} attraverso un'interfaccia compatibile con \texttt{openai}. I pesi dei singoli modelli sono quelli riportati da Meta, in questo caso quantizzati a 4 bit: La precisione numerica dei parametri viene ridotta per contenere la memoria utilizzata, al prezzo di ridurre leggermente la qualità del modello. Questo risulta tuttalpiù un fattore penalizzante per il modello.

Il confine fra parte statica e parte dinamica cade fra la terza e la quarta colonna: i rami che la precedono sono determinati senza eseguire il codice, mentre le quattro foglie richiedono l'esecuzione dei test. L'albero assegna una sola etichetta a ciascun file mentre le metriche sono riportate separatamente.

La foglia \emph{errore a runtime} raccoglie i file che superano il controllo sintattico ma che pytest non riesce a eseguire: l'import della funzione fallisce, oppure non viene raccolta alcuna funzione di test. Questo secondo caso avviene quando il modello produce funzioni cui il nome che non inizia per \texttt{test}che è la convenzione con cui pytest individua i test da eseguire. In entrambi i casi, la suite non produce alcune esito e nessuna metrica è calcolabile.

La foglia \emph{timeout} raccoglie invece le esecuzioni che non terminano entro il limite di tempo previsto di 60 secondi.


\section{Esecuzione e misura}
\label{sec:esecuzione}

\subsection{Procedura di esecuzione}
\label{sec:procedura}
Per ognuno dei file di test $T(m,f)$ viene effettuata la medesima procedura,
identica per tutti i modelli e tutti i campioni.

Il primo passaggio è il controllo sintattico: il file viene passato al parser,
che ne costruisce l'albero sintattico senza eseguire alcuna istruzione. Se la
costruzione fallisce il file risulta non valido e la procedura si interrompe.

I file che superano il controllo vengono copiati in una cartella temporanea. In
questa sono presenti due file complementari: il primo contiene la funzione $f$
sotto test, mentre l'altro contiene i test generati relativi ad essa.
L'esecuzione avviene tramite pytest~\cite{pytest}, con un limite di sessanta
secondi per l'esecuzione. Superato il limite il file viene classificato come
timeout. Contemporaneamente viene misurata la copertura tramite
coverage.py~\cite{coveragepy}, limitata alla sola funzione sotto test.

Ogni campione viene eseguito in una cartella propria perché i test generati
possono lasciare tracce: un file scritto su disco, un modulo caricato in memoria,
una variabile globale modificata. Senza isolamento l'esito di un campione
dipenderebbe da quelli eseguiti prima.

Il campo del dataset che contiene il codice riporta la sola funzione, senza le righe che rendono disponibili i moduli di cui essa si serve. Una funzione che usa re.match per confrontare stringhe, per esempio, presuppone che il modulo re sia stato importato, ma quella riga è rimasta fuori nell'estrazione. Eseguendo il codice così com'è la funzione solleva NameError, per un motivo che non dipende dal modello.

Alla funzione viene perciò anteposto un blocco che importa i moduli di uso comune della libreria standard di Python. Quelle righe sono contrassegnate in modo da non rientrare nel calcolo della copertura, che altrimenti conterebbe istruzioni non appartenenti alla funzione.

\subsection{Misure statiche}
\label{sec:statiche}
Un primo gruppo di misure si ottiene senza eseguire i test, analizzando il file
prodotto e il registro delle generazioni. Riguardano il processo che ha generato
il test più che il test in sé, e sono quelle di cui si è osservata l'assenza
nella Sezione~\ref{sec:comportamento}.

\textbf{Aderenza al formato.} Dei vincoli espressi nel prompt, quattro sono
verificabili meccanicamente sull'albero sintattico del file: la presenza
dell'istruzione di importazione della funzione sotto test, il numero di funzioni
di test compreso fra tre e otto, i nomi conformi allo schema
\texttt{test\_<nome>\_<n>}, e la presenza di almeno un'asserzione in ciascuna
funzione di test. Un file è considerato conforme quando li rispetta tutti.

Su questo vincolo si riportano due misure distinte. La prima conta le sole asserzioni, secondo la lettera della richiesta. La seconda considera conforme anche un test che racchiude la chiamata in un blocco pytest.raises: formalmente privo di asserzioni, ma dotato di un oracolo, poiché verifica che la funzione sollevi l'eccezione attesa.

\textbf{Troncamento.} Per ogni risposta si sa se il modello si è fermato da solo
oppure se ha esaurito i token disponibili. Nel secondo caso il file è incompleto. Il problema è che non sempre si vede: se il taglio cade proprio alla fine di una funzione di test, il file resta sintatticamente valido e sembra a posto. Per questo il troncamento viene contato a parte, invece di affidarsi al solo controllo della sintassi.

\textbf{Tempo di generazione.} Viene registrato il tempo trascorso fra l'invio
della richiesta e la ricezione della risposta. È una misura dell'infrastruttura
oltre che del modello, quindi confrontabile solo fra esecuzioni condotte sulla
stessa macchina e con la stessa quantizzazione.

Un vincolo del prompt resta invece non misurabile: il divieto di produrre
blocchi markdown. La normalizzazione descritta nella
Sezione~\ref{sec:architettura} li rimuove prima che il file venga salvato,
cancellando l'informazione. Se ne conserva traccia soltanto nei casi malformati,
in cui il blocco non è chiuso e la rimozione non lo intercetta.

\subsection{Correttezza} 
\label{sec:correttezza-misura}
Un test passa quando viene eseguito fino in fondo senza che alcuna sua asserzione risulti falsa e senza sollevare eccezioni. Si considera corretto un test che passa sulla funzione fornita dal dataset. La misura di correttezza è il Pass@1: il rapporto fra i test che passano e quelli generati. È la metrica definita nella Sezione~\ref{sec:passa} valutata per $k = 1$, poiché al modello viene
rivolta una sola richiesta per ciascuna funzione.

Il conteggio avviene a livello di test e non di file. Attribuire a ciascun file
una sola etichetta, che indichi se tutti i suoi test sono passati, sarebbe
limitante: come si vedrà nel Capitolo~\ref{ch:risultati}, i file in cui ciò
accade sono pochissimi. È anche il livello al quale la metrica è definita da
Huang et al.~\cite{huang2025ult}, il che rende i risultati confrontabili con
quelli pubblicati.

\subsection{Copertura}
\label{sec:copertura}
La copertura viene misurata sulla sola funzione sotto test,
in due forme: di riga, cioè la quota di istruzioni eseguite, e di ramo, cioè la
quota di diramazioni percorse. La seconda è più severa della prima: in una
funzione con un \texttt{if} tutte le righe possono risultare eseguite anche
percorrendo un solo ramo su due.

Il calcolo viene svolto due volte. La prima con tutti i test del file, e misura
quanto codice viene eseguito. Un test che fallisce esegue comunque la funzione prima di sollevare l'errore: non verifica concretamente nulla ma contribuisce alla copertura. La seconda misurazione si ottiene rieseguendo il file con i soli test che passano e esprime quanto codice viene davvero verificato da un'asserzione corretta. La distanza fra le due dice quanta copertura è prodotta da test che sbagliano.

Ogni misura di copertura è riportata assieme alla base su cui è calcolata. Le basi sono tre: tutti i campioni, attribuendo copertura nulla a quelli non eseguibili; i soli campioni arrivati all'esecuzione, cioè quelli classificati come falliti o passati nell'albero della Sezione~\ref{sec:albero}; i campioni in cui il modello ha importato la funzione sotto test. Se il modello non importa la funzione, i suoi test non riescono nemmeno a chiamarla: la copertura risulta zero, semplicemente perché non arrivano al codice. Misurando sui soli campioni con l'import corretto si vede quanto il modello copre quando quell'ostacolo non c'è.

\subsection{Duplicazione}
\label{sec:duplicazione}
La duplicazione misura quanto un modello ripeta lo stesso caso in più test. È una misura di accompagnamento necessaria al Pass@1: quest'ultimo conta i singoli test, e un modello che un modello che ripete più volte la stessa verifica riuscita ottiene un punteggio più elevato senza che questo sia correlato alla sua effettiva capacità.

Si calcola come numero di righe ripetute sul totale delle righe di test. Le righe vuote e i commenti vengono ignorati. Una riga presente $n$ volte contribuisce $n-1$ volte al calcolo della duplicazione perchè la sua prima apparizione è legittima. Il valore è espresso in percentuale, così da non dipendere dalla lunghezza della suite e restare confrontabile fra modelli.

In questo caso il calcolo avviene su due basi: tutte le righe del file, e
le sole righe appartenenti ai test che passano. La seconda va mediata sui soli
campioni che hanno almeno un test passato: includendo gli altri si sommerebbero
zeri privi di significato, perché in quei file non esistono righe da confrontare.

\subsection{Analisi dei fallimenti}
\label{sec:fallimenti}
L'albero della Sezione~\ref{sec:albero} dice che un campione è fallito, ma non ne spiega il motivo. Per ricostruirne la causa, l'output completo di pytest viene conservato per ogni campione .

Da quell'output si estraggono, per ciascun test fallito, due informazioni: il
tipo di eccezione che ha interrotto l'esecuzione e il file in cui è stata
sollevata. È il secondo dato a permettere la distinzione che interessa. Se
l'eccezione nasce nel file di test, il test non è arrivato a esercitare la
funzione: ha sbagliato il nome, gli argomenti, oppure non l'ha importata. Se
nasce nel file della funzione, quest'ultima è stata chiamata ed è stata lei a
rifiutare l'input ricevuto.

I fallimenti si raggruppano perciò in due famiglie. Si ha un \emph{errore di
oracolo} quando il test esegue la funzione ma ne sbaglia l'aspettativa:
un'asserzione risultata falsa, un'eccezione attesa che non si presenta, oppure
un'eccezione sollevata dalla funzione stessa. Si ha un \emph{errore d'uso}
quando il test non arriva a chiamarla correttamente.

La distinzione è la traduzione empirica di quella introdotta nella
Sezione~\ref{sec:classici} fra il raggiungere il codice e il sapere cosa esso
debba restituire.

\section{Minacce alla validità}
\label{sec:minacce}
Alcune caratteristiche dell'impianto sperimentale possono influire sui risultati
e vanno dichiarate.

\textbf{Codifica dei caratteri.} Tre funzioni del dataset contengono caratteri
non ASCII. I modelli li riproducono nelle proprie asserzioni, e la stampa della
risposta sollevava un errore di codifica che faceva fallire la generazione: quei
tre campioni risultavano persi per una ragione che non riguarda i modelli. Il
problema è stato individuato e corretto forzando la codifica UTF-8 in uscita.
Viene riportato perché mostra come un dettaglio infrastrutturale possa alterare
una misura senza che ciò sia evidente.

\textbf{Riproducibilità.} Alcune funzioni del dataset impiegano numeri
pseudocasuali o dipendono dall'ordine di iterazione, quindi l'esecuzione dei
test non è del tutto deterministica. Fra due esecuzioni successive le medie
oscillano di circa due decimi di punto. I valori riportati vanno letti con
questa approssimazione.

\textbf{Quantizzazione.} La quantizzazione dei pesi, discussa nella Sezione~\ref{sec:modelli}, può solo peggiorare i risultati: quelli riportati non sono quindi sovrastimati.

\textbf{Vincolo non misurabile.} Il rispetto del divieto di produrre blocchi
markdown non è verificabile a posteriori, per la ragione discussa nella
Sezione~\ref{sec:statiche} L'aderenza al formato riportata riguarda quindi
quattro vincoli su cinque.

\textbf{Generalizzabilità.} Lo studio considera cento funzioni di un solo
benchmark, una sola famiglia di modelli e una sola formulazione del prompt.
Quest'ultimo punto merita attenzione: la formulazione del prompt incide sulla
qualità dell'output~\cite{tony2025prompt}, e un template diverso potrebbe
produrre risultati diversi.
